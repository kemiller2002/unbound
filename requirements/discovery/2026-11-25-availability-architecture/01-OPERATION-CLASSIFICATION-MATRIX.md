# 01 — Operation classification matrix

Mission: [README](README.md) · Source data: [`data/operation-classification.jsonl`](data/operation-classification.jsonl) · Status: **proposed** · Implementation: none

Each row classifies an Unbound operation by the INIT-012 request classes
([thin API §2](https://github.com/kemiller2002/echelon-organization-administration/blob/claude/echelon-availability-architecture-ezhitq/application-governance/availability-architecture/03-THIN-API-REQUIREMENTS.md#2-request-classification-model)) and query consistency classes
([standard](https://github.com/kemiller2002/echelon-organization-administration/blob/claude/echelon-availability-architecture-ezhitq/application-governance/availability-architecture/07-QUERY-CONSISTENCY-STANDARD.md)). "Original requirements" are baseline IDs (verified to resolve by
`tools/reqaudit/validate_availability.py`, gate V3) or this mission's `UNB-AVL-*` records.

Reading rules:
* **Queue eligibility** "Yes" means the operation *may* use the durable command path; it does not mean every write is queued.
  Immediate controls are never queued (gate V4).
* **Future cache eligibility** applies only after the adoption criteria in
  [cache-ready §4](https://github.com/kemiller2002/echelon-organization-administration/blob/claude/echelon-availability-architecture-ezhitq/application-governance/availability-architecture/06-CACHE-READY-ARCHITECTURE.md#4-future-adoption-criteria-all-required); release 1 has no cache (UNB-AVL-018).
* A receipt never implies a completed contribution, completed grant, settled transaction or tax-effective date (UNB-AVL-002).
* Unbound never holds or moves money (CNV-LEG-001): "payment" rows relay instructions to sponsor rails and observe outcomes.
